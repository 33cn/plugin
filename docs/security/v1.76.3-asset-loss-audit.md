# plugin v1.76.3 盗币级漏洞审计

> 审计对象：`33cn/plugin` v1.76.3（`06858b7ddd5566ba708ed9894ee402a14c8266f2`，依赖 chain33 `v1.72.7-0.20261016082959-e1bde75e25d0`）
> 范围：只收录可造成**资产被盗/增发/被他人低价拿走**的问题；DoS、信息泄露、纯逻辑错误不计入正文。
> 约定：**已经在现有 PR 中修复/处理的问题全部忽略**（合并进 master 的 #1299/#1303/#1304/#1311/#1319/#1326/#1332/#1333/#1334/#1335/#1337，以及仍处于 open/closed 状态的 #1306/#1308/#1309/#1310/#1312/#1313/#1320）。正文只列 v1.76.3 中仍然存在、且没有任何 PR 覆盖的问题。
> 结论已在本地 v1.76.3 代码快照上逐条复核；lottery 一项用执行器测试实际跑了买入/开奖/关奖三条路径。

## 0. 结论汇总

| # | 模块 | 问题 | 影响 | 级别 |
|---|------|------|------|------|
| 1 | mix | `Withdraw` 同一笔交易内重复 nullifier 双花 | 同一张票据被支付 N 次，直接盗取混币池 | 严重（直接盗币） |
| 2 | mix | `Deposit` 金额按 `uint64` 累加溢出 | 只付零头就把巨额票据记入 Merkle 树，逐张取出盗池 | 严重（直接盗币） |
| 3 | x2ethereum | prophecy 进入 `Success` 后不是终态，额外验证人重复提交同一 claim 会再次铸币/放款 | 跨链资产重复增发、桥侧资金被重复支付 | 严重（增发/盗币） |
| 4 | exchange | `SafeMul`/`caclAVGPrice` 用 `big.Int` 计算后 `Int64()` 静默截断 | 恶意被动买单只冻结零头，成交时按截断后的金额付款，卖方资产被低价拿走 | 严重（盗币） |
| 5 | trade | 挂单/成交金额直接用 `int64` 乘法，溢出后静默回绕；`checkPrice`/`notSameAsset` 参数传错 | 同上，卖方交付资产只收到回绕后的零头；还允许“资产=计价资产”的畸形订单 | 严重（盗币） |
| 6 | multisig | 确认权重使用确认时的历史快照，owner 被修改/删除/替换后仍按旧权重累计 | owner 变更后旧确认仍可凑足阈值，执行当前 owner 集合未授权的转账 | 高（条件性授权绕过） |
| 7 | lottery | `LotteryBuy` 的 `amount*precision` 溢出 | 实付 0.9 枚却记入巨额 Fund；开奖因二次溢出算不出 factor 而永久失败，本轮资金锁定到关奖 | 中（资金锁定/DoS，非直接盗币） |

第 6、7 项按“盗币/财产损失”标准不稳定成立，正文中单独标注了触发条件；第 1–5 项不需要任何特权，普通用户即可发起。

## 1. mix：Withdraw 同交易内重复 nullifier 双花（直接盗池）

**位置**：`plugin/dapp/mix/executor/withdraw.go`

- `spendVerify`（约 15–47 行）逐条校验 proof 时，nullifier 只做了 **读状态** 的存在性检查：
  ```go
  nullifierKey := calcNullifierHashKey(nulliferHash)
  _, err = db.Get(nullifierKey)
  if err == nil { return ErrNulliferHashExist }
  ```
- `Withdraw`（约 91–108 行）循环里对每个 proof 调 `withdrawVerify`，把 nullifier 追加到 `nulliferSet`；**整个循环不写库**。同一笔 payload 里重复放同一个 proof 时，第二次读取的仍是同一份旧状态，检查通过。
- 金额校验用累加和：`sumValue += v.Uint64()`，随后 `sumValue != withdraw.Amount`。重复 N 份 proof 时把 `withdraw.Amount` 也写成 `N*value` 即可通过。
- 付款发生在 loop 之后（约 122 行 `ExecTransfer(execAddr, a.fromaddr, ..., int64(withdraw.Amount))`），nullifier 落库更晚（约 126–131 行），所以整笔交易内没有任何幂等保护。

**攻击**：任意持有一张有效票据（note）的用户，构造
`Withdraw{Amount: N*value, Proofs: [proof, proof, ..., proof]}`，
执行后拿 N 份钱，链上只记录一次 nullifier。N 可以做到池余额允许的上限；单笔转账上限（MaxCoin×precision=1e17）只限制单次金额，不限制重复次数。

**验证**：代码逻辑与 v1.70 完全一致（v1.70→v1.76.3 该文件无实质 diff）；旧分支里已有等价的“同交易重复 proof 双花成功、跨交易重复被拒”的执行器用例（测试代码针对旧 gnark API 未能在本仓库编译，但双花路径本身可由上述代码直接推出）。

**修复**：在同一次 action 内维护 `nullifier -> struct{}` 集合去重；或在付款前先把 nullifier KVs 合并进 receipt 并做二次检查。分叉 `ForkMixDupNullifier` 可平滑上线。

## 2. mix：Deposit 金额 uint64 累加溢出（少付多得）

**位置**：`plugin/dapp/mix/executor/deposit.go`（约 44–75 行）

```go
var sum uint64
for _, p := range deposit.Proofs {
    input, _ := a.depositVerify(p)          // zk 证明只约束 NoteHash=MiMC(...Amount...)
    v, _ := mixTy.VariableToElement(input.Amount)
    sum += v.Uint64()                       // uint64 回绕，无溢出检查
    notes = append(notes, noteHash)
}
...
receipt, err := accoutDb.ExecTransfer(a.fromaddr, execAddr, execAddr, int64(sum)) // 只付回绕后的金额
```

Deposit 电路（`plugin/dapp/mix/types/deposit.go`）只校验
`NoteHash = MiMC(ReceiverPubKey, ReturnPubKey, AuthorizePubKey, Amount, NoteRandom)`，**没有对 Amount 做位宽/上限约束**；合约侧却把 public input 的 Amount 截成 `uint64` 再累加。由于票据金额在树里是按**单张**记账的，存款时的“总和回绕”不会影响之后逐张取款。

**攻击**：
1. 生成 185 张金额约 `1e17` 的票据（每张 `< MaxCoin*precision`，可单笔取出），总面额 `2^64 + 1e8`；
2. 一笔 `Deposit` 提交 185 个 proof：`sum` 回绕成 `1e8`，只支付 1 枚；
3. Merkle 树里 185 张票据都按原面额入树；
4. 逐张 `Withdraw`（每张金额都在单笔上限内），把池里其他用户的存款取走。

**影响**：直接盗取 mix 资金池，利润上限为池子可用余额（实际付出的只有回绕后的零头）。构造 proof 只需要公开的电路/prover，不需要任何特权。

**修复**：累加时用 `big.Int` 或检查 `v.Uint64() > math.MaxInt64-sum`（同时约束单笔总额）；分叉 `ForkMixAmountOverflow` 控制行为。

## 3. x2ethereum：prophecy 成功后仍可重复铸币/放款

**位置**：`plugin/dapp/x2ethereum/executor/x2ethereumdb.go`、`x2ethereumaction.go`

- `Oracle.ProcessClaim`（`x2ethereumdb.go` 约 294–347 行）只在 prophecy 已处于 `Failed` 时拒绝：
  ```go
  if prophecy.Status.Text == x2eTy.EthBridgeStatus_FailedStatusText {
      return nil, x2eTy.ErrProphecyFinalized
  }
  ```
  **`Success` 不是终态**。已成功的 prophecy 仍允许新验证人把同样内容的 claim 加进去，`processCompletion` 会再次算出 `Success` 并返回。
- `procEth2Chain33_lock`（`x2ethereumaction.go` 约 39–116 行）在 `status.Text == Success` 时无条件调用
  `ProcessSuccessfulClaimForLock`（`x2ethereumdb.go` 约 32–54 行），后者执行 **`accDB.Mint(receiverAddress, amount)`**。
- 同一问题在 burn 方向（约 199–270 行 + `ProcessSuccessfulClaimForBurn`）也存在：每次成功都会从桥的 token 账户再转一笔给收款人。

**攻击/触发**：
- 在一笔跨链 lock 的 claim 达到 70% 阈值、第一次铸币之后，任何**尚未提交过该 claim 的活跃验证人**再提交一次相同 claim，就会触发第二次 `Mint`。按 70% 阈值，正常会有约 30% 验证人“迟到”；验证人集变更/轮换后，新验证人还能继续重复。
- 攻击者自己不需要 70% 算力：只要控制其中一个迟到验证人（或者本身就是收款人、等待其他验证人先把 prophecy 推成功），即可对同一笔跨链资产反复增发到自己的收款地址；每次增发都是无抵押通胀，最终由桥/持币人承担。
- 附带缺陷：prophecy ID 用 `chainID||nonce||sender||token||type` **无分隔符拼接**（`x2ethereumaction.go` 约 52 行），不同 `(chainID, nonce)` 组合会产生相同 ID，可让合法跨链 claim 命中已存在的 prophecy 而被判 `Failed`（资金永久卡住）。

**修复**：`Success`/`Failed` 都作为终态（`ProcessClaim` 里直接拒绝）；prophecy ID 改为带分隔符/长度前缀编码；转账地址做大小写归一化。分叉 `ForkX2EthFixReplayCollisionNormalize`。

## 4. exchange：SafeMul / caclAVGPrice int64 静默截断，恶意买单低价成交

**位置**：`plugin/dapp/exchange/executor/exchangedb.go`

```go
// 约 953-958
func SafeMul(x, y, coinPrecision int64) int64 {
    res := big.NewInt(0).Mul(big.NewInt(x), big.NewInt(y))
    res = big.NewInt(0).Div(res, big.NewInt(coinPrecision))
    return res.Int64()          // 超出 int64 时静默截断，不报错
}
// 约 70-76
func CalcActualCost(op int32, amount, price, coinPrecision int64) int64 {
    if op == et.OpBuy { return SafeMul(amount, price, coinPrecision) }
    return amount
}
```

`LimitOrder` 用 `SafeMul` 做买方余额检查/冻结（约 170 行），`matchModel` 成交时用同一个 `SafeMul` 计算付款（约 473、501、531 行）。只要 `amount*price/1e8` 超过 int64，结果就是任意回绕值（可能为小正数，也可能为负数；负数会被 `CheckAmount` 拒绝，但攻击者可以挑出小正数）。

**具体利用（可离线算出参数）**：
- 攻击者挂一笔 **被动买单**：`Amount = 28999941890838049`，`Price = 1e16`（均在 `CheckAmount`/`CheckPrice` 允许范围内）。
  `28999941890838049 * 1e16 / 1e8 = 2.9e24`，截断到 int64 后恰好等于 **256**（0.00000256 枚）。
  这笔买单只冻结 256 个单位，但订单簿上显示的价格是 1e16。
- 当一笔 **taker 卖单**（`Op=Sell`，卖价只要 ≤ 1e16 就会命中）卖出数量 `matched` 时，`matchModel` 先算
  `amount = SafeMul(matched, 被动单价格 1e16, 1e8)`，再 `ExecTransferFrozen(攻击者, 卖方, ..., amount)`。
  若 `matched ≥ 攻击者挂单数量`，则 `matched` 取攻击者挂单数量，`amount` 同样回绕成 256，Frozen 检查通过；随后把 `matched` 个 token 从卖方转给攻击者。
- 结果：攻击者用 0.00000256 枚买走卖方一大堆 token。卖方若继续挂着大额卖单/机器人自动吃最高价买单，会持续被吃单。

同一文件的 `caclAVGPrice`（约 960–966 行）也用 `Int64()` 截断，会写坏订单 `AVGPrice`/市场深度，作为副带问题一并修复。

**修复**：`SafeMul`/`caclAVGPrice` 改为返回 `(int64, error)`，`!IsInt64()` 时拒绝；`CalcActualCost` 同步改签名，在下单和成交两处都检查。

## 5. trade：订单金额溢出 + 价格/资产校验参数错误

**位置**：`plugin/dapp/trade/executor/tradedb.go`、`util.go`

1. `tradeSell`（约 263 行）：`totalAmount := TotalBoardlot * AmountPerBoardlot`，直接 int64 乘法，冻结金额回绕。
2. `tradeBuyLimit`（约 479 行）：`amount := PricePerBoardlot * TotalBoardlot`，同样回绕后返回 `ExecFrozen` 冻结。
3. `tradeSellMarket`（约 562 行）：成交付款 `amount := sellOrder.BoardlotCnt * buyOrder.PricePerBoardlot`，回绕后 `ExecTransferFrozen` 从买单冻结资金付给卖方。
4. `checkPrice`/`notSameAsset` 调用点（约 251–258、474–480 行）把 **`PriceExec` 同时当成 symbol 传入**（应为 `PriceSymbol`）：
   ```go
   checkPrice(cfg, height, sell.PriceExec, sell.PriceExec)   // 2nd arg 应是 sell.PriceSymbol
   notSameAsset(..., sell.PriceExec, sell.PriceExec)         // 同上
   ```
   于是“资产 == 计价资产”的畸形订单在校验中被放过（真正的比较在 `util.go` 的 `notSameAsset` 里，参数传错即失效）。

**利用**：攻击者挂 `BuyLimit` 单，取 `PricePerBoardlot = 2^32`、`TotalBoardlot = 2^32+1`：
`Price*Total = 2^64 + 2^32`，截断后冻结 `2^32`（约 42.95 枚）。卖方用 `SellMarket` 卖出全部 `2^32+1` 个 boardlot 时，付款
`(2^32+1)*2^32 mod 2^64 = 2^32`，正好等于冻结额并通过检查；攻击者按 `AmountPerBoardlot` 拿到大量 token。
`PricePerBoardlot` 在创建/执行层只校验非负（`tradeSell`/`tradeBuyLimit` 开头的 `< 0` 检查），没有上限，参数可以按需构造。

**修复**：所有金额乘法改为带溢出检测的乘法（`big.Int` + `IsInt64`）；`checkPrice`/`notSameAsset` 传入 `PriceSymbol`。

## 6. multisig：确认权重使用过期快照（条件性授权绕过）

**位置**：`plugin/dapp/multisig/executor/multisig.go` 约 934–941 行

```go
func isConfirmed(requiredWeight uint64, multiSigTx *mty.MultiSigTx) bool {
    var totalweight uint64
    for _, owner := range multiSigTx.ConfirmedOwner {
        totalweight += owner.Weight      // 确认时写入的权重快照
    }
    return totalweight >= requiredWeight
}
```

确认时把 `Weight` 写进 `ConfirmedOwner`（`action.go` 约 355、367 行），之后 owner 的 add/del/modify/replace 不会回头修正已有确认。`executeTransferTx`/`executeAccOperateTx`/`executeOwnerOperateTx`（约 760、841、902 行）都用这个过期快照判断阈值。

**影响**：owner 被降权或删除（例如密钥泄露后把该 owner 移出）之后，其历史确认仍按旧权重累计；一笔当时未达阈值的转账可以在 owner 集合变更后“补足”到阈值并被执行，即用**当前 owner 集合并未授权的旧确认**转走多签账户资产。触发需要一笔 pending 交易 + owner 集合变更（降权/删除/替换）同时存在，因此定为条件性高危而非无条件盗币。

**修复**：`isConfirmed` 增加 `multiSigAcc` 参数，按当前 owner 列表重新取权重（已删除的 owner 直接跳过），分叉控制。

## 7. lottery：购买金额溢出（资金锁定/DoS，非直接盗币）

**位置**：`plugin/dapp/lottery/executor/lotterydb.go` 约 356–378 行

```go
receipt, err := action.coinsAccount.ExecTransfer(..., buy.GetAmount()*cfg.GetCoinPrecision())   // 360
receipt, err = action.coinsAccount.ExecFrozen(..., buy.GetAmount()*cfg.GetCoinPrecision())      // 368
lott.Fund += buy.GetAmount()                                                                    // 377
```

`LotteryBuy` 只检查 `buy.GetAmount() > 0`，没有上限。取 `Amount=184467440738` 时 `Amount*1e8` 回绕成 `90448384`：攻击者只付 0.9 枚，`Fund/BuyAmount` 却记成 184467440738。

**本地实测（v1.76.3 快照，执行器测试）**：
- 买入：成功，`buyer` 只扣 90448384，`Fund=184467440738`；
- 开奖：`checkDraw` 里 `factor = precision*Fund/2/totalFund` 再次 int64 溢出（`precision*Fund ≈ 1.8e19`），`factor=0`，随后 `ExecTransferFrozen(..., 0)` 返回 `ErrAmount` → **本轮永远无法开奖**，状态停在 Purchase；
- 关奖：`LotteryClose` 的返还金额同样按 `precision*AmountOneRound` 回绕，恰好等于实付，买家的钱能退回，未产生盗币。

**结论**：不是直接盗币，但攻击者花 0.9 枚就能让任意一轮彩票无法开奖、资金锁到关奖为止（可反复使用）。如果运营方允许长时间挂起或依赖自动开奖，会造成资金冻结/业务中断。建议同样加上限和溢出检查（`ForkLotteryFixOverflow`）。

## 10. 修复记录（分支 `fix/audit-1763-asset-loss`）

以下修复均以 dapp 分叉控制，默认高度 0 生效；关闭分叉（配置为未来高度）时保持旧的共识行为。

| # | 模块 | 分叉名 | 修复要点 |
|---|------|--------|----------|
| 1 | mix | `ForkMixDupNullifier` | `Withdraw` 在 action 内对 nullifier 去重，重复 proof 直接拒绝 |
| 2 | mix | `ForkMixAmountOverflow` | `Deposit` 累加前校验 `v.Uint64() > MaxInt64-sum`，溢出拒绝 |
| 3 | x2ethereum | `ForkX2EthFixReplayCollisionNormalize` | `Success`/`Failed` 作为 prophecy 终态；prophecy ID 改为分隔符编码 |
| 4 | exchange | `ForkFixSafeMulOverflow` | `SafeMul`/`caclAVGPrice` 返回溢出错误；下单、冻结、撤单、成交、均价计算全部在分叉后拒绝溢出 |
| 5 | trade | `ForkTradeFixOverflow` | 卖出冻结额、买单冻结额、吃单/吃卖单的付款与 token 数量均做溢出检测；`checkPrice`/`notSameAsset` 改传 `PriceSymbol` |
| 6 | multisig | `ForkMultiSigFixStaleWeight` | `isConfirmed` 分叉后按 owner 当前权重重算，删除/降权的 owner 不再计入 |
| 7 | lottery | `ForkLotteryFixOverflow` | `LotteryBuy` 拒绝 `amount*precision` 溢出及超过最大发行量的金额 |
